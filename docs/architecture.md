# Architecture (Phase 0)

## Layers

1. **Database (PostgreSQL 16).** The last line of defence. Rules that must hold no matter what the application does live here as constraints and triggers:
   - `journal_entry_balanced`: deferred constraint trigger; at commit every entry has two or more lines and debits equal credits in each currency.
   - `reject_mutation`: `UPDATE`, `DELETE` and `TRUNCATE` on `journal_entries`, `journal_lines` and `audit_events` raise `IMMUTABLE`. Periods can change status but never their dates, and can't be deleted.
   - `journal_lines_same_tx`: lines can only be added in the transaction that created the entry.
   - `journal_entries_check_period`: the entry date must fall inside its period; locked periods refuse everything; soft-closed periods need the session flag `app.allow_soft_closed`.
   - Composite foreign keys tie every line's account and entry to the same organisation and entity.
   - Row-level security on every table, keyed on `app.org_id`. The application connects as the owner but each tenant transaction runs `SET LOCAL ROLE altqbo_app`, which has no `BYPASSRLS`.
   - `audit_heads_forward_only`: the chain head can only advance by one, to the newest event.

2. **Services (`src/core`).** `postJournal` is the only writer to the ledger. It resolves accounts by code or system key, checks roles, enforces idempotency (same key + same content returns the original; same key + different content is refused), assigns the next gapless number, and appends the audit event in the same transaction.

3. **Rules (`src/rules`).** Plain data, deep-frozen at load, hashed. `resolveRules(place, date)` returns the federal and state packs in force; every pay run records `id@version#hash` for the packs it used. `jurisdictions.ts` lists the countries (the United States live; Canada and its provinces and territories planned) and each one's states or provinces, live or planned; a business can only be set up in a live one. Every state is one `StateRulePack` (kind `state`): a withholding method (`none`, California's `ca_method_b`, or an employee-elected percentage like Arizona's A-4), its other payroll taxes (SDI, UI, ETT...) each with a code, agency, rate, wage base and liability account, deposit rules (`ca_edd`, `quarterly`, `federal_timing_by_average`), quarterly forms, W-2 box 14 lines, the employer account number's format, wage-and-hour rules (minimum wage with mid-year changes, daily or weekly-only overtime, paid sick leave or none, new-hire reporting) and business rules. Adding a state is a new pack plus its entry in `LIVE`; a new withholding method or deposit rule is the only code it can need. Canada will add a country-level pack the same way.

4. **Payroll (`src/payroll`).** Pure functions: hours split (daily rules where the state has them, else 40 a week), federal Worksheet 1A, state withholding by the pack's method (`state-withholding.ts`), gross-to-net over whatever taxes the state pack lists. `approveAndPostPayRun` adds the two-person rule, freezes the figures in the audit log, and posts one entry per run.

5. **Invoices and bills (`src/core/documents.ts`).** Ported from the Ledgerline prototype, where these rules ran only in the browser. Triggers on `documents`, `document_lines` and `document_payments` enforce: line amount = quantity x price and tax = rate on taxable lines (rounded half-up); totals = sum of lines; at commit, a document must have a posting entry that carries its total to receivables or payables; an issued document only changes by voiding, which must point at the reversal of its entry and is refused once payments exist; a payment can't exceed the amount due and must be backed by its own entry. Invoice and bill numbers are gapless per entity.

6. **Bank feed (`src/core/bank.ts`).** Statement lines are imported into `bank_lines` with a dedupe key per bank account (date, amount, description and which repeat it is in the file), so overlapping statements import safely and the database refuses the same line twice. Imported lines never change. A recorded line must point at an entry that moves exactly its amount through that bank account; a categorised line returns to review only after its entry is reversed, and a line that paid an invoice or bill stays recorded. The journal's reverse action refuses entries owned by invoices, bills, payments and bank lines, so those records can't drift from the ledger.

7. **Reconciliation (`src/core/reconcile.ts`).** A completed reconciliation records the statement date and balance, the beginning balance and the cleared journal lines. The database requires each one to start from the previous statement's ending balance, to be dated after it, and (at commit) for beginning + cleared lines = statement balance. A journal line can be cleared only once, only on its own bank account and only if dated on or before the statement. Reconciliations are append-only.

8. **Reports and books health (`src/core/statements.ts`).** Every report is a query over posted journal lines grouped by each account's statement line, so reports can't disagree with the trial balance. The balance sheet doesn't depend on a closing entry: income before the fiscal year start shows as prior years' earnings and income since as current year earnings. The health check reads the same data and only reports; it never changes the books.

9. **Team (`src/app/team.ts`).** An invitation stores the email, role and a SHA-256 hash of a random link token; it expires after 14 days. Accepting needs the token and a signed-in user with the invited email, so a forwarded link is useless to anyone else. The database lets an invitation settle once (accepted or revoked, never edited or deleted), refuses acceptance by a different email or after expiry, and checks at commit that every organisation still has an owner. Invitations, role changes, removals and leaving are in the audit chain.

10. **Chart of accounts (`src/core/accounts.ts`).** New accounts are added by kind (bank account, credit card, expense and so on), which fixes the type, subtype, statement line and cash-flow class; receivables, payables and payroll control accounts stay system-only. Tax lines can only be codes the entity's template already uses for its return and account type. A trigger on `accounts` refuses a statement line that doesn't suit the type, any change to code, type, subtype or system key, deleting, and deactivating a system account or one with a balance. A trigger on `journal_lines` refuses posting to an inactive account and takes a share lock on the account, so a deactivation and a posting can't cross.

## Money

Amounts are `bigint` minor units with a currency everywhere outside the tax math. Rates and per-period tax math use `decimal.js` (40 digits), rounding half-up to cents only at the end of each tax. Postgres `int8` parses as `BigInt`. No floats touch money.

## Audit chain

Each event's hash is SHA-256 over the canonical JSON (sorted keys) of its fields plus the previous hash. The first event chains from `sha256("alt-qbo:audit-genesis:" + orgId)`. `verifyAuditChain` recomputes the chain and checks the head, so it catches edits made by anyone who disabled the triggers, and deleted events, including the last one. A later step is anchoring the head hash externally (for example, a daily signed checkpoint) so a full rewrite of chain and head is also detectable.

11. **Overview and closing (`src/core/overview.ts`).** The money figures are read from posted lines and open documents on the same basis as the reports, and the menu badges come from one counting query run on every screen. Closing the books through a date is a loop over `setPeriodStatus`, so it obeys the same role checks and audit events as closing one month, plus one `books.closed_through` event; it never reopens anything. The example business is built with the ordinary services (`issueDocument`, `recordPayment`, `importBankCsv`) in a separate organisation, one per person.

12. **Email (`src/app/email-auth.ts`).** Sign-in, reset and confirmation links each carry a random 32-byte token; `email_tokens` keeps its SHA-256 hash, purpose, the address it went to and an expiry (15 minutes, an hour, three days). A trigger lets a token be spent once, before it expires, and never edited or deleted. A token stops working if the account's email changes, and spending any token marks the email confirmed. Links are built from the configured site address (`APP_URL`, or Netlify's `URL`), never the request's Host header. The request forms answer the same way whether or not an account exists.

13. **Sales tax (`src/core/sales-tax.ts`).** Taxability is data: the state's sales-tax rule pack maps each kind of sale to taxable or not, with the regulation it rests on. `issueInvoice` decides the tax before the invoice exists, in a fixed order (an owner's or accountant's rate set by hand with a reason; nothing taxable; a resale certificate; delivery outside the state; otherwise the CDTFA rate for the customer's address, or the business's), refuses a looked-up rate outside the state's possible range rather than use it, and passes the decision to `issueDocument`, which stores the rate (five decimals, so 8.625% is exact), its source, the address and the jurisdiction on the invoice. The database keeps every line's rate equal to the invoice's, requires a note for a rate set by hand and an address for a looked-up one, and allows tax only on invoices. A retried invoice replays the stored decision instead of looking the rate up again. Rate lookups are cached for a few hours for the live preview on the invoice screen.

14. **Backup (`src/core/backup.ts`).** A backup is the entity's rows from every bookkeeping table, read in one transaction so they are consistent, plus the whole organisation's audit events and their verification. The download is appended to the audit chain first, so the file contains its own record. A SHA-256 over the canonical JSON of the entity, tables and events lets `verifyBackup` spot a changed or damaged file. Restoring from a backup is not built yet.

15. **Employees and pay runs (`src/payroll/employees.ts`, `src/payroll/runs.ts`).** Employees keep their pay (annual salary or hourly rate), W-4 and DE 4 choices, per-paycheck deductions, sick leave balance and any wages paid earlier in the year before TrailBook. A pay run copies these into its saved input when prepared, so later edits never change it. Year-to-date wages are summed from posted runs (and the earlier-in-the-year figures) every time a run is calculated, including again at approval, so a run approved after another one posts still stops Social Security, FUTA and UI at their wage bases. Approval also moves each hourly employee's sick leave balance forward. Social Security numbers are sealed with AES-256-GCM under `PII_KEY` (32 bytes, base64, set on the server, never in the database); the database, audit log and backups only ever see the last four digits. Pay stubs show what Labor Code 226 asks for: the employer's name and address, the last four of the SSN or an employee ID, the period, hours and rates, gross, each deduction, net pay and sick leave available.

16. **Direct deposit (`src/payroll/nacha.ts`, `src/payroll/direct-deposit.ts`).** Each employee may have one checking or savings account; the business stores what its bank gives it for ACH origination (routing number, company ID and immediate origin, which default to "1" and the EIN). Account numbers are sealed under `PII_KEY` like SSNs, and only their last four digits reach the database's readable columns, the audit log and backups. For a posted run, `directDepositFile` builds a NACHA file with one PPD batch of credits (transaction codes 22 and 32) dated the pay date, plus an offsetting debit from the business account when the bank wants a balanced file. Routing numbers are checked with the ABA check digit; records are 94 characters, padded to blocks of ten. Employees without an account are listed for a paper check. The business uploads the file to its own bank; TrailBook never moves money. Only owners, admins, approvers and accountants can download the file, and each download is in the audit chain.

17. **Tax deposits (`src/payroll/deposits.ts`, `src/payroll/tax-deposits.ts`, `src/payroll/deposit-reminders.ts`).** What's due is worked out from posted pay runs every time it's shown, never stored, so it can't drift from the runs. Liabilities arise on the pay date. Form 941 taxes follow the business's federal schedule (monthly by the 15th; semiweekly by the third business day after each Wednesday-Friday or Saturday-Tuesday period, split at quarter ends; $100,000 next-day, after which a monthly depositor is semiweekly), and a quarter under $2,500 isn't late until Form 941 is due. FUTA is deposited at a quarter's end once more than $500 is owed. State taxes follow the state pack's deposit rules: California PIT and SDI go quarterly, monthly or on the federal semiweekly timing depending on accumulated PIT; UI everywhere is quarterly with the wage report; Arizona-style withholding follows the federal dates when last year's quarterly average was over the threshold. Thresholds come from the rule packs. Federal dates move past weekends and DC legal holidays; California dates move past weekends and only the holidays the state shares with the federal calendar, and other states' dates past weekends only, so a date shown is never later than the real one. Recording a payment posts an entry from a bank account to the liability accounts (`tax_deposit` entries can't be reversed from the journal), and the database checks the entry pays exactly that amount; payments are append-only. A daily scheduled function (`netlify/functions/deposit-reminders.mts`, 15:00 UTC) emails owners, admins and accountants once when a deposit is within five days of its due date and once if it is missed (missed within the last two weeks only); example businesses get none.

18. **Prepared forms (`src/payroll/forms.ts`).** Forms 941, 940, the state's quarterly forms from its pack (California's DE 9 with DE 9C; elsewhere a UI wage report or a withholding return built by `formStateQuarterly`), and W-2 with W-3 (state boxes 15 to 17 only where the state has income tax) are worked out from posted pay runs and recorded tax deposits each time they're opened, like the deposit list, so they can't drift from the books. Each comes back as numbered lines with notes and warnings (missing EIN, address, EDD account number or SSNs; wages paid before TrailBook; a FUTA credit reduction not yet announced), plus a CSV of the per-employee rows. The 941's tax liability is by month, or by day on Schedule B for semiweekly depositors. The business's state payroll account number (EDD in California) is stored on the entity in `state_employer_id` and checked against the state pack's format; assigned rates such as UI are in `state_tax_rates` by tax code. Full SSNs are only unsealed for owners, admins and accountants, and each time is recorded in the audit chain; everyone else sees the last four digits. TrailBook doesn't file anything: the business or its accountant copies the figures into the filing site.

19. **Connected apps (`src/app/oauth.ts`, `src/app/public-api.ts`, `src/app/milepost.ts`).** TrailBook is an OAuth 2.0 provider (authorization code with rotating refresh tokens) for apps registered on the server; MilePost is the first. An owner or admin allows an app for one business on the consent page; codes, access and refresh tokens are random and only their SHA-256 hashes are stored, outside the tenant boundary like sessions. A code or refresh token used twice revokes the grant. Each `/api/v1` call checks the token, its scopes, that the approver is still an owner or admin (with two-factor if the organisation requires it) and, for changes, that the subscription is active, then works inside the tenant transaction as `app:<name>` with bookkeeper permissions. `external_refs` maps the app's ids to TrailBook customers and invoices, so a repeated request returns the first record; an app can only read invoices it created. In the other direction, a MilePost API key is sealed under `PII_KEY` in `app_links` and used only on the server for the MilePost tab. See `docs/milepost-integration.md`.

## Not in Phase 0 yet

- Multi-currency functional amounts and revaluation (lines carry a currency and balance per currency today).
- Filling the official PDF forms, Schedule R, 941-X and W-2c corrections, and a W-2 e-file (EFW2) file; working out the federal lookback period from TrailBook's own history; reversing a recorded tax deposit.
- Splitting a paycheck across several bank accounts, prenote (zero-dollar test) entries, and bank holidays when checking the pay date.
- Sick leave used, final paychecks, voiding a posted pay run.
- A self-service reset for someone who lost both their phone and their recovery codes.
- City minimum wages, regular-rate overtime for bonuses, supplemental-rate withholding.
- Sales tax outside California, use tax on purchases, prepayments.
- Restoring a business from a backup file into the database (backups are taken nightly, read back and checked, but loading one back in is still a manual job).
